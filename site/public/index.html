Igarapé

From idea to production

Igarapé is a CLI that generates Python service repositories ready for coding agents.

Igarapé is in early development and available on PyPI.

Quick start View on GitHub

Why Igarapé

Coding agents write code fast. Without a shared process they also ship unspecified behavior, untested requirements and unreviewed security, and every team configures its agent differently.

Igarapé is a golden path for Python services built with coding agents: one command creates a production-ready repository where the process, the quality bar and the delivery pipeline are already in place, whichever agent the team uses.

  • One SDLC for every agent.

    The same AGENTS.md and .agents/skills/ are read by Codex, Claude Code, GitHub Copilot and OpenCode; each agent gets only a thin adapter generated from the same source

  • A real service, not a blank repo.

    import-linter keeps the layers apart (domain and application import no framework); integrations are generated only when chosen, with no dead code.

  • Quality gates the agent cannot talk its way around.

    make check runs Ruff (PEP 8/257 and Bandit rules), mypy --strict, import-linter, pip-audit on the locked tree and pytest with branch coverage ≥ 90%, identically on a laptop, in an agent session and in CI.

  • Security by default.

    Security, contract (Schemathesis) and property (Hypothesis) tests ship with the service. CI runs gitleaks, zizmor and Trivy, with actions pinned by commit SHA and least-privilege permissions.

  • Delivery verified in production (optional).

    A deploy is done only when the smoke test confirms the deployed version (the release version, else the commit SHA) and readiness; otherwise it rolls back automatically.

  • Projects keep improving.

    Generated repositories stay linked to the template; copier update brings later improvements.

Igarapé does not replace your coding agent or invent new tooling.

How it works

Every generated project ships the same six-phase process as skills in .agents/skills/. Each phase produces a versioned artifact and ends at a gate.

  1. Discovery $discovery Gate: problem and metrics approved
  2. Specify $specify Gate: acceptance criteria approved
  3. Plan $plan Gate: plan approved
  4. Implement $implement Gate: make check green
  5. Review $review Gate: no blocking findings
  6. Ship $ship Then: CI, merge, optional CD

A well-scoped local fix may start at implement with a regression test.

The agent guidance is written once in a shared core; each selected agent gets only a thin adapter in the format it reads.

Agents supported

AGENTS.md, the skills and the four roles are written once; each selected agent only gets the adapter its format requires.

  • Codex .codex/agents/*.toml
  • Claude Code .claude/agents/*.md
  • GitHub Copilot .github/agents/*.agent.md
  • OpenCode .opencode/agents/*.md

AGENTS.md, seven skills (discovery, specify, plan, implement, integrate, review, ship) and four subagent roles (architect, test_engineer, reviewer, security_auditor).

Quick start

Requirements: uv, Git and make. Docker is needed only for the optional integrations.

uvx igarape new orders-api
cd orders-api && make bootstrap && make run   # in-memory API on http://127.0.0.1:8000
make check                                    # the Definition of Done gate

Then open the directory with your coding agent. It reads AGENTS.md first.

Install it for repeated use with uv tool install igarape.

Why you can trust it

Template CI runs on every pull request and every push to main:

  • ruff check + ruff format --check

    The CLI and tests are clean.

  • uv run pytest

    All 6 scenarios render with the expected layout; every agent adapter renders the shared roles with the right permissions; the CLI rejects invalid input without touching the destination

  • uv run pytest -m smoke

    The built wheel generates the default service, which starts, becomes ready and creates and reads an item over HTTP.

  • zizmor

    The workflows of a project generated with all four agents, and this repository's own, have no medium+ findings.

  • Property-based tests (Hypothesis)

    The CLI's external input (--mcp NAME=URL) only accepts credential-free HTTPS endpoints, and nothing it accepts can break out of the generated TOML/JSON config.

  • Pinned base images

    The generated Dockerfile pins both base images by digest for Python 3.12, 3.13 and 3.14.

  • make check × 6 scenarios

    Each generated project passes its own gate: all-agents, full-kafka, minimal, postgres-rabbit, redis-only, with-mcp, with real PostgreSQL, Redis, Kafka and RabbitMQ in containers.

  • Generated images

    The Dockerfile builds for the in-memory and full (Postgres + Redis + Kafka) profiles; the in-memory container starts and reports the build version; the full image packages its entrypoints and migrations; Trivy fails on fixable HIGH/CRITICAL CVEs.

Repository controls: actions pinned by commit SHA, permissions: {} by default, checkout without persisted credentials, Dependabot for actions and Python dependencies

Why the name

Igarapé comes from Tupi: igara (canoe) + pé (path), "the canoe's path", the narrow waterways that cross the Amazon forest. The process is the igarapé; every coding agent is an igara travelling the same path to production.
